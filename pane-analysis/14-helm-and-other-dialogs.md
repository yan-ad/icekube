# Helm panes and global dialogs

Analysis-only extension: [shared inspector](06-shared-inspector.md), [earlier validation](07-validation.md), [expanded validation](15-expanded-validation.md). Freelens source is pinned at `cd07118f843c4a69f937a319a37a7c12ef2c92d8` / `v1.10.3-533-gcd07118f`; Iceon HEAD is `e71baf2d51d2be391485d52dd837f428dc8d21aa` with concurrent dirty work. Source observations below are of the inspected working tree, not release certification. `packages/...` means Freelens root; `src/...` / `src-tauri/...` means Iceon root. No app launch, cluster/Helm operation, real kubeconfig/credential read, tests, install, upstream change or source adaptation was performed.

**Seven distinct surfaces** are counted here. Charts, chart details/install, and release details/actions must not be collapsed into “Helm supported.” Catalog forms, saved metadata and Preferences are global Astryx dialogs, **not resource drawers**. Updater implementation is outside this audit; the install editor's update blocker is noted only for modal ownership.

## Helm Charts catalog

**Freelens:** `packages/core/src/renderer/components/helm-charts/helm-charts.tsx:122-143` lists **Name (with chart identity/icon), Description, Version, App Version, Repository**. Chart selection opens the dedicated chart drawer, not a Kubernetes object inspector. Repository is separately visible/filterable in that view; chart versions/readme are requested separately by detail services. This is a configured-repository catalog, not proof of an authenticated or connected Kubernetes read.

**Iceon:** actual renderer is `src/app/cluster/HelmTablePage.tsx:88-120`, not the unused Helm column recipe in `resourceViews.ts`. Charts columns are **Name, Version, App version, Description**. Name and context-menu Details open a local **summary** with Kind, Name, Version, App version, optional Description (`:65-78`); chart row context also offers Install, with loading/error/pending guards (`:80-86`). Repository is encoded in `repository/chart` name but has no separate column/filter or provenance detail. The global bottom-right Install button opens the same installation editor without selected chart context. Local search covers only loaded DTO rows; it does not discover additional repositories or chart versions.

**Rust scope and lifecycle:** `src-tauri/src/connection/helm.rs:337-352` uses fixed `helm search repo -o json`; no shell, repo-update or install side effect. It reads the local Helm cache, not Artifact Hub or live repository verification. The workspace requires a connected lease to mount this surface (`src/app/cluster/ClusterWorkspacePage.tsx:87-100`), but that is not evidence chart search itself queries Kubernetes. `helm.rs:14-15,184-204` bounds output to 2 MiB per pipe and rows to 500; DTO fields are explicit, not chart metadata JSON. `HelmTablePage.tsx:35-56,104-118` scopes old replies, polls at 30 seconds, cancels exact old reads, distinguishes first loading/retained refresh/error/empty/filtered-empty/partial. Install context pauses polling while selected. Partial is not total repository inventory; a trusted CLI cache refresh remains external to this UI. No Kubernetes permission table alone proves Helm executable/repository access.

## Helm installation dialog (upstream dock workflow)

**Freelens:** `packages/core/src/renderer/components/dock/install-chart/view.tsx:43-132` shows repository/name badge, version selector, namespace selector, optional custom release name, **Force conflicts**, values/configuration editor, submit/cancel, and configuration-loading/error states. Success offers **View Helm Release** and **Show Notes**/execution output. `dock/install-chart/install-chart-model.injectable.tsx:159-165,221-230,257-269` requests default chart values/version changes and sends selected release parameters. The renderer API posts `/v2/releases` (`packages/core/src/common/k8s-api/endpoints/helm-releases.api/request-create.injectable.ts:25-40`); this is upstream backend integration, not a renderer-owned Helm subprocess. `packages/core/src/main/helm/install-helm-chart.injectable.ts:44-86` writes temporary values, runs fixed install/version/namespace/kubeconfig arguments, generates a release name when omitted, and consumes force-conflicts/server-side preference flags. The inspected namespace selector itself does not establish namespace creation. Do not transplant its Node architecture.

**Iceon fields and exact click flow:** `src/app/cluster/HelmInstall.tsx:33-39,46-51,103-125` is an intentional Astryx modal instead of dock tab. It shows cluster name/ID/context; **Namespace** (specific loaded namespace, no All), **Release name** required, optional **Cached chart** selector, **Chart repository/name**, optional **Chart version**, **Values YAML** initially `{}`. Context Install fills chart name/version. **Run server dry-run** submits first; successful validation changes title to **Confirm Helm installation**, shows exact namespace/release/chart/version (or “Repository default (not pinned)”), hides values, then **Install release** sends the same frozen input with a fresh request ID. **Edit installation** invalidates validation. No default chart-values fetch, create-namespace, force-conflicts, user-configurable wait/timeout, arbitrary flags/URLs, OCI/local archive picker, or Helm upgrade substitute is present.

**Rust validation/ownership:** `src-tauri/src/connection/helm_install.rs:4-5,143-200` requires DNS-safe namespace and release (63/53), exactly safe `repo/chart`, bounded optional version and a single mapping YAML document, values ≤256 KiB. Arguments are fixed: `install <release> <repo/chart> --namespace <ns> --values <private-temp> --output json --timeout 60s`; optional `--version=…`; dry-run adds `--dry-run=server --hide-secret`, real install adds `--wait`. `:202-213` admits Helm 3.17+ or major 4; `:216-278` checks session, registers one owned install lane, prepares selected-context temporary kubeconfig/values, supervises process with 120-second deadline and cleanup. Shared supervisor `connection/helm.rs:424-455` clears Helm override/proxy environment variables, sets fixed KUBECONFIG/secret driver, uses pipes/null stdin and process group/job ownership; remaining supervision bounds, kill/reap and status handling are in that service. Values/kubeconfig/raw stderr are not returned as renderer logs. Chart reference is configured-repository provenance, **not cryptographic chart verification**; an unpinned version can resolve differently between dry-run and install, as UI explicitly warns. A successful renderer dry-run flag is not a durable Rust-issued review token or universal future authorization grant.

**Failure/staleness/cancel:** `HelmInstall.tsx:58-99` cancels exact active read on close/unmount; ignores late completions; namespace changes invalidate validation; sent requests mark uncertainty. `:20,118-125` warns installation may already have reached the cluster and cancellation does not roll it back. Success closes editor and refreshes **current inventory**, not both pages, release details, or a new live watch. Section/session disposal owns process cancellation, not transactional rollback; empty result after refresh is not proof a canceled release never existed. Helm actual chart resources determine RBAC; CRD create, namespace create, hooks and Secrets access cannot be reduced to one static write permission. Existing table permission UI is not complete Helm authorization gating.

## Helm Releases and release details/history/resources/values/actions

**Freelens list:** `packages/core/src/renderer/components/helm-releases/releases.tsx:167-184` has **Name, Namespace, Chart, Revision, Version, App Version, Status, Updated** and per-release menus. Details are Helm-specific, not generic Kubernetes details. `helm-releases/release-details/release-details-content.tsx:40-97,112-169` shows **Chart + Upgrade**, **Updated** relative/absolute, **Namespace, Version, Status**, editable **Values** with **User-supplied values only** toggle and **Save**, optional Notes content, and grouped Resources (kind heading; **Name link, conditional Namespace**). Model uses details/configuration APIs, grouping only actual returned resources (`release-details-model/release-details-model.injectable.tsx:112-141,173-212,232-243`); unavailable detail shows explicit load failure/spinner. Values Save is a release update, **not a local text preference**. Resource links use API version/kind resolution, not `helm list` name parsing.

**History and destructive routes:** `packages/core/src/renderer/components/helm-releases/release-menu.tsx:32-89` offers Upgrade, conditional Rollback only for revision >1, and Remove confirmation. Upgrade creates a dock upgrade tab and can hide drawer; Remove delegates delete-release service, whose backend executes `helm delete <name> --namespace <namespace> --kubeconfig <proxy-config>` (`packages/core/src/main/helm/delete-helm-release.injectable.ts:24-34`). **History here is the rollback dialog**, not a demonstrated standalone history tab: `helm-releases/dialog/dialog.tsx:48-82,93-125` fetches history for exact release name/namespace, sorts newest revision first, shows revision/chart/app-version/update options, empty revision state, then Rollback sends chosen revision and notifies on failure. This source does not prove closing its dialog cancels an already sent mutation.

**Iceon actual list:** `src/app/cluster/HelmTablePage.tsx:88-98` shows **Name, Namespace, Chart, App version, Status, Revision, Updated**. Chart DTO string is not a separately parsed Chart + Version pair; upstream's distinct Version column is missing. Namespace button opens Namespace resource details, not a release filter gesture. List uses fixed `helm list --all` with either `--namespace` or `--all-namespaces`, output JSON (`src-tauri/src/connection/helm.rs:337-352`), selected-context temporary config and the same bounded supervisor. Helm secret-driver reads require cluster permission; namespace discovery separately requires namespaces LIST. All namespaces is server/Helm scope, while Search/Status filter only the loaded ≤500 rows. Helm may impose its own lower limit, explicitly stated in `HelmTablePage.tsx:116`.

**Iceon summary, not full detail:** `HelmTablePage.tsx:65-78` captures **Kind, Name, Chart, App version; conditional Namespace, Description, Revision, Updated; status**. There is **no release detail/history/configuration/manifest/notes GET**, no grouped child resources, no values view/editor, no upgrade, rollback or uninstall action. Release context menu is Details only (`:82-86`); bottom-right plus installs a new chart, not an upgrade to selected release. Generic Kubernetes Delete cannot uninstall a Helm release. Table loading/error/stale/partial/cancel behavior is as above; summary freshness is not a named live read and current inventory polling is not history polling.

## Catalog Add config / Add web link

These are Catalog workflow dialogs, not upstream resource drawers. Freelens Add Cluster exists as its own global route/workflow (`packages/core/src/features/add-cluster/navigation-using-application-menu.test.tsx`); it is not the behavioral authority for credential-bearing raw-object resource panes. Iceon intentionally retains Catalog-first sections and metadata-only import. No one-to-one upstream equivalent for the restricted saved web-link form is asserted.

**Exact fields/actions:** `src/app/catalog/CatalogForms.tsx:28-88,93-207` opens **Import kubeconfig** from Add config: explanatory metadata-only/no-auth copy, **Kubeconfig path**, **Choose File**, Cancel, **Import contexts**. Add web link has **Name, URL**, Cancel, **Save web link**. Validation/error is visible, missing inputs disable submit; busy state prevents closing and picker conflicts. Picker session serial invalidates late selection on dialog switch/disposal; file picker cancel is not import. Rust commands are `catalog_import_kubeconfig({path})` and `catalog_add_web_link({name,url})`; opening form alone submits neither. Browser preview disables native/domain operations.

**Filesystem/metadata authority:** `src-tauri/src/catalog.rs:314-343,440-484,554-580,614-648` owns bounded selected-file reads/parsing and saved records. Input symlinks are canonicalized to readable regular bounded targets; canonical identity plus selected-path provenance survives successful import. Broken/cyclic links preserve prior records; catalog/lock/sidecar storage symlinks are not allowed by analogy. Import stores context metadata, not credentials or auth execution. Built-in default discovery is only `~/.kube/config`, not environment/directory scanning (`catalog.rs:410-438`); discovery failure is different from losing saved records. These claims are source inspection, not real-file experiments.

**Saved-ID opener restriction:** saving a link does not contact it. `catalog.rs:525-550` accepts normalized HTTP(S) without credentials/query/fragment. Activation calls Rust `catalog_open_web_link` by **saved ID**; `catalog.rs:254-276` re-reads saved record, validates ID and stored URL, releases catalog lock, then asks OS opener. Missing/corrupt/stale ID and OS failure are distinct failures. This is **not blanket external permission**, arbitrary renderer URL opening, filesystem access, shell access, or `window.open`. `src-tauri/capabilities/default.json:5-12` grants window controls/core only, not general renderer opener permission. Pin/Remove must not activate the row; saved metadata does not imply a live authenticated connection.

## Preferences (global, not resource drawer)

**Reference scope:** `packages/core/src/features/preferences/renderer/preferences.tsx:29-47,51-75` renders SettingLayout + hierarchical preference navigation, close/back and missing-page fallback; extensible tabs are not a promise Iceon supports Freelens extensions. This global settings surface is distinct from per-cluster resource details. Iceon intentionally uses one **Preferences** Astryx modal (`src/app/preferences/PreferencesDialog.tsx:12-20,103-139`), opened by toolbar/native integration and Cmd/Ctrl+, (`PreferencesProvider.tsx:47-75`), with local section buttons and no resource selection/history URL.

**Exact exposed settings** (`PreferencesDialog.tsx:140-311`):

- **App:** Color Theme (System/Light/Dark); Locale Timezone (System, UTC, America/New_York, Europe/London, Asia/Tokyo); Restore last page; Persistent search; Start-up; Menu-bar Settings.
- **Proxy:** HTTP / HTTPS Proxy URL; Certificate Trust / Allow untrusted CAs.
- **Kubernetes:** Helm Binaries Path; Server-side apply; Kubeconfig discovery.
- **Editor:** Font size; Tab size; Font family; Line numbers (On/Off/Relative/Interval); Minimap; Minimap position (Right/Left).
- **Terminal:** Font size; Font family; Terminal theme (Match app/Dark/Light); Terminal copy & paste; Terminal Shell Path.
- Footer **Reset to defaults, Cancel, Save changes**, saving indicator, error alert/success status (`:72-100,313-320`). Reset saves defaults immediately; it is not just resetting the unsaved draft. Ordinary draft changes apply after Save, not live preview. Opening copies current preferences into draft (`:62-68`); read/save/reset authority is Rust (`PreferencesProvider.tsx:88-102`, `src-tauri/src/preferences.rs:155-175,185-216,359-402`), with SQLite revision-conflict protection. Theme/editor-font presentation consumption exists (`PreferencesProvider.tsx:78-85,117`), not proof every option's advertised native/backend effect works.

**Honest limitations:** initial preference read failure is silently retained as prior/default snapshot and `preferencesReady=true` (`PreferencesProvider.tsx:30-40`), not a visible failed-load pane. Save/reset errors are visible; saved/dirty/conflict/initial-load are not all separately surfaced. Dialog onOpenChange can close during saving even though footer Cancel is disabled (`PreferencesDialog.tsx:108,318-320`); completion uses an unowned 500ms close timer (`:79-81`), so close/reopen during save deserves a stale-result test, not a claim it has been proven safe. Labels do not establish effects: inspected Helm services select executable through their own PATH lookup (`connection/helm.rs:356-365`) and explicitly clear proxies (`:441-446`); installation arguments do not consume preference `helm_server_side` (`helm_install.rs:179-200`). Persisted **Helm Binaries Path / Server-side apply / proxy** settings therefore cannot be credited as operating those workflows merely because Save succeeds. Native startup/tray, full terminal/editor integration, and TLS policy effects require separate consumer verification; do not relax TLS to make an option appear functional. Updater internals are not audited here.

**Coordinating fixture follow-up:** the existing save-feedback test failed in the 94-test sweep and all three isolated repeats. `PreferencesProvider.save` updates the snapshot, triggering the dialog's `[isOpen, preferences]` effect that clears status, competing with the success text set by `handleSave`. See [15](15-expanded-validation.md) for the exact result and separate persistence probe. This does not prove preferences were not saved and is not fixed by this documentation task.
