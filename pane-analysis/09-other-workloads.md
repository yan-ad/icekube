## Shared contract, verified for these five panes

- Iceon has a dedicated route/list for every kind, not placeholder navigation: `src/app/cluster/resourceViews.ts:52-85`. Ordered table columns are assembled at `src/app/cluster/ResourceTablePage.tsx:59-73`; checkbox selection is a table plugin, not an Actions data column. The five lists all have Name, Namespace, their registered columns, Age, Status. Their generic inspector renders Name, Namespace link, Created, UID, resource version, projected columns/relationships and bounded sections (`ResourceInspector.tsx:201-243`). These are **present**, not full upstream detail equivalents.
- Shared upstream metadata includes Created, Deleted, Name, Namespace link, optionally UID/selfLink/version, Labels, Annotations, Finalizers, owner links, expandable managed fields (`F/kube-object-meta/kube-object-meta.tsx:90-160`). Iceon does not expose the full label/annotation/finalizer/managed-fields view in these generic panes. Selectors are not metadata labels. This is **partial**, with sensitive annotation policy still required, not permission to send arbitrary JSON.
- Iceon details validate exact API/kind/name/namespace and expected UID; response carries session/read identity (`src-tauri/src/connection/details.rs:198-257`). `controlled_owner` admits one controller, exact allowlisted API/kind and same namespace, retains UID, rejects ambiguous controllers (`details.rs:500-545`); namespace links are rendered for all five. The backend can return controller references (`details.rs:398-415`), but only Pods receive the `controlledBy` projected column (`resources.rs:423-426`), and the inspector only renders relations attached to item columns (`ResourceInspector.tsx:235-237`). Thus ReplicaSet→Deployment and Job→CronJob are **backend-only capabilities, not reachable links in these panes**. There is no parent→children collection in this DTO.
- API identities are concrete: StatefulSet/ReplicaSet use `apps/v1` namespaced `statefulsets`/`replicasets`; ReplicationController uses core `v1` `replicationcontrollers`; Job/CronJob use `batch/v1` `jobs`/`cronjobs`. Iceon generic detail/mutation mappings delegate to `src-tauri/src/connection/create.rs:66-70,124-128`; the per-kind upstream detail registrations match exactly these versions (`F/kube-object-details/kube-object-detail-items/implementations/{stateful-set,replica-set,replication-controller,job,cron-job}-detail-item.injectable.ts:30-32`). Thus HTTP targets below mean `/apis/apps/v1/namespaces/<ns>/<plural>/<name>`, `/api/v1/namespaces/<ns>/replicationcontrollers/<name>`, or `/apis/batch/v1/namespaces/<ns>/<plural>/<name>`; scale adds `/scale`, trigger POSTs the namespaced Jobs collection. None of these workload actions requires a host subprocess.
- Generic conditions expose Type, Status, Reason, Last transition, not message/heartbeat (`src-tauri/src/connection/detail_facts.rs:935-950`). Limits are 12 sections, 32 facts/section, 12 collection entries, 1024-byte values, 64 KiB total with explicit Coverage partial marker (`detail_facts.rs:5-9,39-102,174-204`). Missing scalar is “Not reported”; do not synthesize zero or false.
- **Actions present elsewhere:** all five can create a metadata scaffold through server dry-run/review, and delete selected rows or a context-menu target (`src/app/cluster/ResourceActions.tsx:15-32`, `RowContextMenu.tsx:110-138`). Creation is not an edit, scale, trigger or clone workflow. Generic inspector header has no non-Pod mutation menu (`ResourceInspector.tsx:142-175`). Context menu for these kinds is Details/Delete, not YAML edit (`RowContextMenu.tsx:119-123`).
- Iceon delete requires verified get+delete for each target and captured namespace/name/UID/resourceVersion; dialog names cluster/context and all targets, normal grace/finalizers, serial results; Cancel before send has no write, Stop deleting cancels active work/stops future work but expressly cannot roll back accepted work (`src/app/cluster/ResourceDelete.tsx:48-141`). No force/finalize option in these generic panes. This is an **intentional safety boundary**, not an absent deletion engine.
- Upstream generic menu exposes Edit where store.patch exists and delete modes based on latest store object; terminating objects with finalizers get Force Finalize, others Delete (`F/kube-object-menu/kube-object-menu.tsx:163-177,188-282`). Confirm identifies namespace/name/cluster, then hides details and submits. Finalize is merge PATCH `metadata.finalizers=[]`; force is grace zero/Background (`kube-object-delete-service.injectable.ts:23-56`). Do not substitute Iceon's guarded deletion with these name/selfLink operations.
- Upstream YAML edit is a dock workflow with managed-fields/sort toggles; it diffs the first draft to JSON Patch, chooses edited selfLink and reports failure/success (`F/dock/edit-resource/edit-resource-model/edit-resource-model.injectable.tsx:118-127,265-361,413-469`). No explicit UID/resourceVersion test is inserted into the shown generated patch. Closing a dialog/tab is not evidence that a submitted request is aborted. Upstream resource-specific controls below do not show effective-rights gating; server errors remain authoritative. - Upstream associated Events is registered for all objects (`F/kube-object-details/kube-object-detail-items/implementations/kube-event-detail-item.injectable.ts:12-21`) and subscribes/unsubscribes on pane mount/dispose, newest-lastTimestamp first, message/source/count/sub-object/last seen (`F/events/kube-event-details.tsx:45-98`). ## Delivery boundary and priority

This chapter defines **23 resource-specific acceptance checklist items** (5+5+3+5+5). They are neither automated results nor an estimate of implementation size. Highest-risk work is adding writes without UID/RV/auth baselines, replaying uncertain CronJob creates, copying upstream immediate RC scaling, disclosing full templates/annotations through generic YAML, and confusing inverse suspend labels or active refs with complete owned-child inventories. Source inspection found actual upstream presentation quirks; behavioral reference does not require copying those defects. Keep React presentation, Rust Kubernetes ownership and Astryx shell as specified in `DESIGN.md:5-20,33-40,54-61`.
