## Common inventory, inspector, and operation contract

This contract applies to all ten built-in kinds, with per-kind differences below. Users uses a separate engine/editor.

### Tables, scope, sorting, filtering

- Iceon common visible columns are selection checkbox, **Name**, **Namespace only for namespaced kinds**, the per-kind columns below, **Age**, **Status**, and row **Actions**. `src/app/cluster/ResourceTablePage.tsx:59-73,203-232`; `src/app/cluster/RowContextMenu.tsx:81-103`. Name is a button, not whole-row activation. Namespace is a typed Namespace detail link. Age is derived from creation time; invalid/future/missing becomes N/A (`ResourceTablePage.tsx:50-57`). Namespaced kinds here are ServiceAccounts, Roles, RoleBindings only (`src-tauri/src/connection/resources.rs:5-34`).
- Initial namespace is `""` => **All namespaces**, not kubeconfig/default namespace; initial query/status/group are empty. Scope/filter change resets continuation and disposes obsolete reads (`ResourceTablePage.tsx:76-90,143-158`). The selector lazily lists at most 1,000 namespaces/10 pages; offers local option search, partial/error/empty feedback, retry, and known-namespace entry when discovery is denied/unverified (`src/app/cluster/NamespaceScope.tsx:23-85,102-136`). All namespaces is list scope, not an authorization grant. Generic creation's own target defaults to `default` when no specific table namespace is selected.
- No header sorting plugin/callback is installed on these Iceon tables. Rust sorts the **returned page** by `(namespace,name)` (`src-tauri/src/connection/transport.rs:151,266`); this is not a globally sorted complete cluster inventory. Search is a case-insensitive substring over name, namespace, status and every projected column value; no label/UID search unless explicitly projected. Status is exact-match; Group is CRD-only (`transport.rs:283-309`; `ResourceTablePage.tsx:208-217`). Projection-only fields listed below are searchable and shown in inspector metadata even if not visible table columns. Status is generally `Unknown`, not healthy or authorized (`resources.rs:333-350`).
- Unfiltered pages return at most 100 items, 2 MiB response; filtered scans stop at 10 pages/1,000 scanned items and retain continuation. Never interpret `100+`, truncated, or filtered-empty as full absence (`transport.rs:12-20,90-167`). These are foreground bounded snapshots, with 10-second auto-refresh paused on later pages/pending search; no RBAC/admission WATCH toggle (`ResourceTablePage.tsx:119-158`).
- Freelens per-kind columns/sort callbacks are enumerated below. All use configurable shared list layout, search fields, row detail toggle and generic menu; namespaced APIs gain the shared namespace filter (`F:C/kube-object-list-layout/kube-object-list-layout.tsx:248-295`). Namespace storage defaults to `[default]` if allowed, otherwise first allowed namespace, with persisted selection (`F:packages/core/src/features/namespace-filtering/renderer/storage.injectable.ts:20-24`), **not Iceon's fresh All scope**. Common search fields are name, namespace, UID and labels (`F:packages/kube-object/src/kube-object.ts:217-219`). Resource callbacks add subjects/volumes/rules where specified. Sorting supports ascending/descending, persisted per table and URL sync; no per-kind initial sort is supplied in the inspected views. Shared Table returns input order when sortBy/orderBy is absent (`F:C/table/table.tsx:161-165,203-230`; `F:C/item-object-list/content.tsx:566-577`). The underlying store normally orders by name (`F:packages/core/src/common/item.store.ts:24-31,77-82`); Role, ClusterRole and both Binding stores explicitly order kind then name (`F:U/roles/store.ts:14-17`, `cluster-roles/store.ts:14-17`, `role-bindings/store.ts:16-19`, `cluster-role-bindings/store.ts:21-23`). Thus fresh same-kind store inventory is name-ordered unless persisted/URL table sorting overrides it; do not confuse absence of an active table sort with random API order. Age callback is negative creation timestamp (ascending => newer first). Array sort uses elementwise comparison (`F:C/table/sorting.ts:11-46`).

### Inspector fields and safety bounds

All Iceon resource details show Status, Name, optional linked Namespace, Created, UID, resourceVersion and **all projected item columns**, then flat fact sections. Missing metadata renders Unknown; absent table values render N/A. Sections contain text, not arbitrary JSON or child tables (`src/app/cluster/ResourceInspector.tsx:225-244`). Pane controls for these ten kinds are Refresh, Expand/Restore and Close, with separator/keyboard resizing and guarded Escape; **no YAML edit, finalize, token reveal, or Delete in the pane header** (`ResourceInspector.tsx:141-194`). Details/Delete are the row menu's only applicable actions; Pod-only edit/logs/exec/attach/forward branches do not apply (`RowContextMenu.tsx:115-139`).

Rust fact limits are **12 sections, 32 facts per section, 1,024 bytes per scalar, 12 array entries**, with escaped aggregate budget 64 KiB and a reserved Coverage marker (`src-tauri/src/connection/detail_facts.rs:5-9,22-128,174-204`). `fields` emits Not reported for missing/null/unsupported scalar; `rows` emits only present scalar subfields, numbers rows, skips missing arrays and caps entries; `strings` emits first 12 valid strings per array. Invalid controls/bidi or oversize values are omitted rather than shortened. Core RBAC API group `""` becomes `(core)`. Overflow/malformed supported values marks Partial, and coverage can displace the twelfth section. **Unsupported field families that are never traversed do not automatically trigger Partial**: a pane with no Coverage marker is not a full object dump. All kinds also attempt Conditions rows: type, status, reason, lastTransitionTime; no message/lastHeartbeatTime, first 12 rows/32 facts (`detail_facts.rs:936-950`). Multiple fields per row can exhaust 32 facts before 12 complete rows: webhook policies fit four complete seven-field rows plus four fields of row five; binding subjects eight complete four-field rows. This is a fact-budget truncation, not a Kubernetes rule-count limit.

Details GET is bounded to 2 MiB; apiVersion/kind/name/namespace/UID are checked and stale session/read IDs rejected (`src-tauri/src/connection/transport.rs:538-553`; `src-tauri/src/connection/details.rs:104-257`). Refresh can retain explicit stale facts on failure. Namespace relation is generated for namespaced resources; role/policy links require reviewed reference validation (`details.rs:260-285,347-366`). No generic subject, webhook-Service, parameter-object, or Secret relationship list is synthesized.

Upstream resource detail components below are **registered**, not merely exported: `F:C/kube-object-details/kube-object-detail-items/implementations/register-injectables.ts:56-61,141,181,206-226,246-256`. They are enabled by matching kind/apiVersion, not proof the API exists or current credentials permit it (e.g. `service-account-detail-item.injectable.ts:20-30`, `pod-security-policy-detail-item.injectable.ts:20-30`, `validating-admission-policies-details-item.injectable.ts:20-34`). Shared metadata/labels/annotations/owners/finalizers/managed fields and header copy behavior are distinct from kind-specific sections; see chapter 06. Iceon does not acquire those features merely by projecting UID/version.

### Generic create, dry-run, delete, and upstream actions

**Present, with limitations:** all ten Iceon kinds have a creation mapping and generic create/delete path (`src/app/cluster/resourceViews.ts:324-337`; `ResourceTablePage.tsx:228-232`). Create is the bottom action overlay: with an explicit namespace or cluster-scoped kind its launcher requires observed allowed create access; from an All-namespaces namespaced table the launcher instead requires allowed list, then the dialog checks create for its selected namespace (`src/app/cluster/ResourceCreate.tsx:30-35,51-54`). The dialog shows cluster/context/ID, kind/API and target namespace, metadata-only YAML scaffold, Validate YAML, confirmation, Edit YAML, Create and Cancel/Cancel request. It is not a complete Role/Binding/webhook/policy form (`src/app/cluster/ResourceCreate.tsx:25-42,45-128`). Rust accepts one YAML object, at most 256 KiB, fixed kind/version, valid explicit name/ns; rejects status/server-owned metadata and multi-document input, then POSTs the allowlisted collection, `?dryRun=All` when validating (`src-tauri/src/connection/create.rs:13-14,178-260,295-309,376-415`). Response content is not displayed as raw object. Kubernetes enforces schemas, escalation/bind permissions and admission. A removed API cannot be made available by a scaffold.

**Important distinction:** generic creation's dry-run-before-confirm is UI state, not a backend stored, expiring one-shot plan. `CreateRequest` exposes `dry_run: bool`; the backend independently authorizes each request, but does not demand a previous approved dry-run token (`create.rs:16-27,295-309`). Do not conflate this with Users' 120-second plan. Generic creation also validates names as DNS subdomains (`create.rs:204-210`), whereas reads permit RBAC path-segment names including `system:…` (`details.rs:54-77`): creating colon-named RBAC objects through this dialog is a **partial compatibility gap**.

Delete supports selected visible rows or row menu, confirmation of captured targets and sequential submissions; UI checks exact GET/delete permission, disables stale scope, stops queues, retains per-item errors and uncertainty, and deselects accepted targets (`src/app/cluster/ResourceDelete.tsx:22-144`; `ResourceSelection.tsx`; `RowContextMenu.tsx:118-136`). Rust authorizes GET+DELETE, preflights current UID/resourceVersion, then DELETEs with both preconditions and Background propagation; even HTTP 200 may mean accepted/pending finalizers, not disappearance (`src-tauri/src/connection/delete.rs:120-141,211-297`). No generic force-delete, remove-finalizers, collection-delete or automatic rollback/retry. Missing UID/version prevents selection/deletion, not inspection.

Upstream generic **Edit** and **Delete/Force Finalize** are wired through the shared list and details menu, not a hypothetical per-kind menu. Edit is enabled by store.patch/updateAction and opens an edit-resource tab; deletion by store.remove/removeAction. For non-Pods, terminating+finalizers selects Force Finalize; otherwise normal Delete, with confirmation and hide-details before service submission (`F:C/kube-object-menu/kube-object-menu.tsx:163-178,203-283`; `F:C/kube-object-list-layout/kube-object-list-layout.tsx:273-280`). Force Finalize merges `metadata.finalizers=[]`; it is not force deletion (`F:C/kube-object-menu/kube-object-delete-service.injectable.ts:30-55`). Shared selection also offers confirmed removal (`F:C/item-object-list/content.tsx:583-588`). These source capability checks are not equivalent to Iceon's explicit SSAR/epoch guards, nor a promise upstream never receives Forbidden. No dedicated admission/PSP Add wizard is supplied by their inspected list components. Generic upstream edit is separate from the dedicated access-control Create/subject-edit dialogs described below.

**Common gap acceptance:** Rust owners `connection/create.rs`, `delete.rs`, `details.rs`, `transport.rs`, plus typed presentation adapters. Keep loading, empty, filtered-empty, denied, access-unverified, stale, partial, API-unavailable, conflict, submitting and canceled/uncertain distinct. For sorting/filter parity, fixtures must show label/UID search omission and per-page ordering vs complete inventory. For future edit/finalize, require explicit approval, bounded editable schema, exact UID/version/authorization baseline, review and non-rollback outcomes; test changed identity/finalizers, Forbidden, 404 and timeout before offering controls. Never add renderer Kubernetes networking or reuse Users' privilege plan implicitly.

### Exact grants vs names and effective access

Rust copies actual selected template rules, preserving groups/resources/verbs/resourceNames/nonResourceURLs; no automatic seed roles/namespaces or wildcard additions. “Namespaced”/“cluster” **prefixes classify templates by name**, not a discovery-verified constraint that all listed resources have that scope. Per-namespace assignment makes a RoleBinding to the ClusterRole; All namespaces and cluster template produce ClusterRoleBindings. Binding names are deterministic hashes; each targets exactly the managed SA namespace/name (`rbac_management.rs:460-495,1004-1052`). Consequently **All namespaces binds the exact template cluster-wide**, including any cluster-scoped resources/non-resource URLs the template already grants. It is not safe to describe this as “namespaced-only access” based on the prefix. UI must retain exact rules/wildcard warning and never equate a scope label with a privilege restriction.

Read classification accepts resource get/list/watch only, rejects wildcard API groups/resources and path segments exec/attach/portforward/proxy; non-resource rules must use get only. Write classification preserves chosen actual rules, not automatic '*' write privileges (`rbac_management.rs:74-88,985-1000`). Read templates can still grant Secret reads or sensitive URL GETs. None removes only this managed assignment selection; **it cannot revoke unrelated grants**, group membership, external authorizers or other bindings. Account settings enforce `automountServiceAccountToken=false`, strip Secret/imagePullSecret reference fields on outgoing updates; no TokenRequest, token Secret, kubeconfig/export/reveal (`rbac_management.rs:1084-1117`). Saving is not authentication as that user.

### Plan, permission, baseline and lifecycle trace

Thin registered commands: `cluster_rbac_management_snapshot`, `cluster_rbac_user_plan`, `cluster_rbac_user_apply`, `cluster_rbac_management_cancel` (`src-tauri/src/lib.rs:40-65,593-596`); typed closed request/response validators `src/app/cluster/managedUsersApi.ts:8-50` onward. Rust owns single active management lane, monotonic read ID, cancellation and stale delivery rejection; cannot replace an executing mutation lane (`rbac_management.rs:505-576`).

1. Plan validates explicit namespace/name, paired UID/RV for updates/deletes, bounded assignments/64 KiB saved user; GETs Namespace and exact account, confirms create absence or exact existing identity, loads saved prior assignments and selected templates by exact GET/UID/RV. Existing deterministic bindings must match owner manager/SA UID, exact roleRef and **exactly one** subject; unrelated subject or ownership mismatch => Conflict, not adoption (`rbac_management.rs:387-434,595-658,1055-1082`).
2. Reconciles previous managed assignments only: removed old bindings delete, account create/update, missing desired bindings create; unchanged desired bindings retained with preflight baselines. Delete removes saved managed bindings then account. At most 128 operation steps. Every intended mutation gets exact action/scope/name authorization, preflight and server dry-run **including DELETE dry-run**; post dry-runs an opaque random plan is stored with auth epoch and **120-second monotonic deadline** (`rbac_management.rs:659-741,300-320,1182-1224`). SSAR create/update/delete is not a substitute for Kubernetes bind/escalate checks; server dry-run remains authoritative. Reads themselves also need server GET/list access; UI write checks alone are not a complete privilege manifest.
3. Apply rejects wrong plan/read/session, expired monotonic deadline or invalid epoch, **takes plan once before executing**, validates templates/retained and pending binding/account baselines again, and reauthorizes each submission. PUT for account update, POST for create, DELETE with UID+RV preconditions. New account's real UID feeds subsequent binding ownership annotation; `pending-dry-run` never becomes real ownership (`rbac_management.rs:743-839,1146-1224`).
4. Per-step results are applied/failed/notSubmitted; first error stops subsequent submissions. No rollback, replay or reusable confirmation. Cancellation/disconnect/timeouts can leave a request accepted on server; failure is **not proof of no write**. Results are preserved even after disconnect where possible (`rbac_management.rs:780-867`; `ManagedUserEditor.tsx:81-118,130-133`). Wire messages are safe codes with 2 MiB bounded bodies, not raw diagnostics (`rbac_management.rs:1231-1292`).

**Gap/risk owner/states/acceptance:** `connection/rbac_management.rs` and `permissions.rs` remain owners; React only renders exact plans. Highest-risk fixtures: all-namespaces template containing cluster resources/URLs, wildcard grants, unrelated external binding, changed template UID/RV, account replacement, extra binding subject, mixed selected/unselected namespaces, denied binding create vs allowed SA create, bind/escalate dry-run rejection, expired epoch with same boolean decisions, second-step failure, accepted POST followed by cancel, delete preconditions. UI must distinguish no managed accounts from partial/unreadable source, exact saved grants from effective rights, no cluster selection from no access, dry-run success from applied, and canceled from rolled back. Proposed improvements: explain dangerous all-namespace template scope explicitly; surface structured non-secret binding ownership/conflict diagnostics; if a true view-permissions report is approved, implement separately with coverage of authorizers and unknowns, not a union of visible rules advertised as effective. Existing source tests include `src-tauri/src/connection/rbac_management/tests.rs:69-227,293-342,532-710,798,936` and `tests/managed-users.spec.ts:37-190`; no execution result claimed.

## Coverage, highest risks, and validation handoff

This chapter covers **ten dedicated built-in-kind sections plus Users**, separating table columns from projection-only inspector fields, namespace defaults from actual grant scope, and registered upstream actions from unused exports. Most ordinary inventories and identity guards are present; most richer upstream structured inspectors are partial. Users is deliberately a different product workflow, not a missing clone. PSP/version availability and native/live behavior remain unavailable evidence.

Priority review items for the main validation pass:

1. **Privilege meaning:** all-namespace managed templates become ClusterRoleBindings; prefixes/Read labels are not resource-scope or effective-access guarantees. Preserve actual rule review, wildcard warnings and unrelated-grant caveat. Never claim deleting a managed user revokes all external access or invalidates issued credentials.
2. **Plan boundaries:** Users' one-shot 120-second monotonic auth-epoch plan is distinct from generic creation's UI dry-run confirmation. Failed/canceled submissions remain uncertain; no rollback. Test both paths rather than assuming shared guarantees.
3. **Silent inspection gaps:** generic Partial markers describe traversed-field limits, not every omitted schema field. ClusterRole nonResourceURLs/aggregation and policy CEL/audit/parameter selectors are materially absent even when no partial marker appears. Rules/subjects/webhooks can exhaust facts mid-row.
4. **Reference correctness:** preserve Iceon's kind-aware Role vs ClusterRole link; do not copy upstream LinkToRole ambiguity. Missing subject/Webhook Service/parameter links require reviewed typed DTO changes, not inferred object paths.
5. **Credential boundary:** SA reveal/kubeconfig export and webhook CA/raw URL/TLS payloads are not supported read features. Upstream whole-object YAML editing is not a reason to broaden Iceon's redaction or capabilities. Generic manifest creation is user-authored submission, not permission to export existing credentials.
6. **API and name compatibility:** fixed admission v1 and legacy PSP requests need unavailable/denied states, never fake empty/healthy. RBAC read paths accept names generic Create's DNS validation rejects. Future write parity must not weaken identity/precondition checks to bypass that mismatch.
