### What “message” actually means

There are three different workflows, and they must not be conflated:

1. **Cluster → Message** in Freelens is the `ClusterIssues` table. A row can originate from a **Node warning condition** or a filtered Kubernetes Warning Event. Clicking anywhere on the row, including its message, opens the **affected object** drawer, not necessarily an Event drawer. Evidence: `packages/core/src/renderer/components/cluster/cluster-issues.tsx:92–149`.
2. **Workloads → Overview → Events → Message** is an Event row. The generic row details action targets the **Event itself**. Its Involved Object link separately opens the affected object; its Namespace badge changes the namespace filter. Evidence: `packages/core/src/renderer/components/events/events.tsx:164–223`, `packages/core/src/renderer/components/kube-object-list-layout/kube-object-list-layout.tsx:278–280`, `packages/core/src/renderer/components/namespaces/namespace-select-badge.tsx:35–49`.
3. **Event details → Message / Event summary** concerns detail content, not a separate Kubernetes resource or route. Freelens explicitly renders the Event's message and involved-object fields; Iceon's “Event summary” is a Rust-projected detail section and does **not** recover a full message omitted from inventory projection. Evidence: `packages/core/src/renderer/components/events/event-details.tsx:48–83`; `src-tauri/src/connection/detail_facts.rs:729–740`; `src/app/cluster/ResourceInspector.tsx:227–243`.

Iceon's Cluster currently calls its message column **Event message** and the section **Latest warning events**. That is honestly a different workflow from Freelens's combined **Cluster issues**; renaming alone will not close the gap.

### Important bounded-read nuance

The Cluster UI says “one page” of 100 warning events. This is **one renderer `cluster_resources` response**, not necessarily one Kubernetes LIST HTTP request. `status: "Warning"` is applied by Rust projection/filtering, **not** a Kubernetes `fieldSelector`: `src-tauri/src/connection/transport.rs:98–145,283–308,353–372`. Rust can scan multiple bounded pages until enough matching items/deadline/scan bound. It returns a continuation/truncated state. This still cannot guarantee the globally most recent warnings: the returned set is not server-sorted by occurrence. The UI correctly avoids that guarantee (`src/app/cluster/ClusterOverview.tsx:347–352`), but the “one page” explanation can be read too literally.

## 4. Exact action chains, inspector content, and RBAC effects

### A. Cluster warning Message versus related object

**Freelens:** Node condition/Event warning → issue `selfLink` (Node directly, Event via involvedObject API lookup) → row click `toggleDetails(selfLink)` → resource drawer. This is inspection, not mutation. An Event-origin warning typically opens the involved Pod/other resource, not the Event (`packages/core/src/renderer/components/cluster/cluster-issues.tsx:95–115,130–149`).

**Iceon:** Message text does nothing. Involved object or Namespace button → `openRelated` retaining the **Event** identity → inspector `PermissionGate` reviews Event GET → `cluster_resource_detail` → Rust session/UID-checked Event GET → derive relation → `navigateResource` → target resource section → target inspector GET (or Pod's specialized details). Missing/unsupported relation fails rather than guessing. Read-only Event → relation → target lookups require Event GET plus target GET and applicable discovery/permission-review requests; entering target inventory can also cause LIST. Namespace resolution additionally requires Namespace GET, unlike an upstream namespace-filter badge.

Evidence: `src/app/cluster/ClusterOverview.tsx:378–419`; `src/app/cluster/ResourceInspector.tsx:50–68,182–184,206–220`; `src/app/cluster/PermissionGate.tsx:8–14`; `src-tauri/src/connection/details.rs:133–170,212–249,464–498`.

Rust relation acceptance requires supported exact apiVersion/kind, valid target name and UID, matching namespace for namespaced targets, and consistent `involvedObject`/`regarding` if both occur. Event row display only projects `/involvedObject/kind,name`; a regarding-only relation may therefore exist in details without an overview relation button (`src-tauri/src/connection/resources.rs:829–835`; `src-tauri/src/connection/details.rs:491–498`). This is an additional presentation/contract gap, not permission to guess from text.

### B. Workloads Event Details

Actions → Details (also right-click or Shift+F10/ContextMenu) → `openResource({kind:"events",namespace,name,uid})` → PermissionGate/Event GET → right inspector. The page supplies **only details**, not delete/edit/logs/shell/forward. This chain does not mutate Kubernetes. A native/browser menu response is discarded when captured rows/session/scope change; shared menu has fingerprint guards (`src/app/cluster/RowContextMenu.tsx:24–70,84–103`). A Details item being offered is not proof the Event GET is allowed: overview action array itself does not use the permission-aware `useResourceRowActions`; the inspector gate/server decides.

- **Present (match/partial):** identity, Namespace link, created time, UID, resourceVersion, projected Event columns (message/reason/type/source/count/occurrence times/involved-object where present), additional Event summary facts. `src/app/cluster/ResourceInspector.tsx:227–243`; `src-tauri/src/connection/resources.rs:785–839`; `src-tauri/src/connection/detail_facts.rs:729–740`.
- **Missing versus Freelens detail:** complete message beyond row projection, involved-object Field Path, dedicated Name/Namespace/Kind/Field Path table, reactive duration + absolute first/last occurrence presentation. Freelens evidence: `packages/core/src/renderer/components/events/event-details.tsx:48–83`. Iceon raw timestamps/facts are not equivalent to a full Event document.
- **Summary clarification:** `openSummary` is a distinct renderer-only fact-panel API, but neither overview message invokes it. “Event summary” is a subsection returned by Rust inside normal resource details, not a full-message fallback (`src/app/cluster/ResourceInspector.tsx:61–68,179–184`; `src-tauri/src/connection/detail_facts.rs:729–740`).
- **Intentional security bounds:** sanitized 256-byte Event column values; no raw objects/configuration/credential dump. Sanitization protects text structure, not confidentiality of arbitrary Event prose. A diagnostic-message improvement must be explicitly reviewed, bounded, cancellable, and disclose truncation (`src-tauri/src/connection/resources.rs:841–854`; `DESIGN.md:786–790`).

### C. Inspector controls and failures

- Open moves focus to labelled Resource details region; close returns focus to connected trigger. Escape closes unless editable control/menu/dialog owns interaction. Resize separator supports pointer, arrows, Home/End; expand/restore/close are named buttons. **match** usable inspection intent, source-evidenced only. `src/app/cluster/ResourceInspector.tsx:44–52,115–175`.
- Refresh details button and Cmd/Ctrl+R act on the selected resource, not the overview behind it; disabled while loading. Normal overview refresh registers separately. `src/app/cluster/ResourceInspector.tsx:127–138,173`; `src/app/cluster/WorkspaceRefresh.tsx:57–61`.
- Late replies ignored and detail request canceled on selection/disposal; stale retained detail content remains marked on refresh failure. UID mismatch produces replaced-resource message; notFound/unsupported relationship has explicit refresh guidance. `src/app/cluster/ResourceInspector.tsx:206–226`; `src-tauri/src/connection/details.rs:212–231`.
- **Unproven:** native menu presentation, narrow pane drag behavior, actual OS keyboard/focus behavior and cross-platform accessibility. Source handlers do not establish successful native interaction.

### D. Shared backend ownership and authorization

There is no dedicated Rust overview endpoint: both overviews use typed `cluster_resources` and `cluster_resources_cancel`; details use `cluster_resource_detail` and its cancellation command (`src/app/cluster/api.ts:173–179`; `src/app/cluster/detailApi.ts:133–140`; `src-tauri/src/lib.rs:314–320,346–365`).

`ConnectionEngine::resources` validates request/session/read ID, rejects **known denied LIST**, bounds worker concurrency, uses session client/credential validation, replaces older same-kind read tokens, rejects stale completion, and bounds network operation. Unknown permission is not an allow guarantee; the API server can deny it. `src-tauri/src/connection.rs:687–762`. Resource detail validates scope/identity, session, credentials and UID; the inspected details function does not show the same explicit known-denied precheck as LIST, so do not claim every GET is backend-preflight-gated. UI PermissionGate is not server authorization. Kubernetes GET/LIST/RBAC remain the authoritative effect, with no write required for the audited overview gestures.

## 6. Concrete gap owners and acceptance scenarios

All scenarios below are **proposed**, not executed results. Use fixtures/mock Rust transport; no real kubeconfig or live mutation is necessary.

1. **Cluster message activation (P1).** Owner: React `ClusterOverview.tsx`; Rust `connection/details.rs` plus proposed overview/issues service. Given a Node pressure condition and an Event about Pod UID A, clicking/Enter/Space on each issue message opens the correct Node/Pod inspector, not a summary or Event by mistake. Nested relation/menu actions must not double-activate. Deleted/replaced Event/target, unknown kind, conflicting regarding/involvedObject, RBAC GET denial, and stale session each give explicit safe failures.
2. **Cluster issue aggregation (P1).** Rust owns bounded Node condition projection and Event/Pod joins, object-UID grouping and completeness. 3. **Workload Event row/message (P1).** React owns row activation; Rust existing detail GET owns identity. Click/Enter/Space Message opens Event inspector. Involved Object opens target only, namespace action performs its explicitly named behavior only, Actions/Shift+F10 does not activate row. 4. **Namespace continuity (P1).** UI owns one explicit context model and route propagation; Rust transport owns selected namespace LIST scope. Click Event Namespace B and verify intended parity behavior updates shared filter and re-reads widgets/events without navigating to Namespace details; if retaining details behavior instead, label it accordingly and provide separate filter action.
