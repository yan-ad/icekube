# Local macOS comparison: Iceon and Freelens

Measured on 2026-10-29 using the installed applications. Neither application was
built, replaced, or launched with benchmark-specific runtime flags.

## Environment and workload

- Apple M4, 10 logical CPUs, 16 GiB RAM, macOS 27.0.1 (26A434), AC power.
- Iceon 0.0.6 and Freelens 1.10.3, both ARM64, installed in `/Applications`.
- The user confirmed and reconfirmed that both apps were connected to the same
  cluster and namespace, showed matching Pod counts, and had visible, settled
  Pods lists without inspectors, logs, terminals, or port forwards.
- No deliberate interactions during capture. Existing profiles and background
  behavior remained enabled; both applications ran concurrently.
- macOS denied Accessibility access. View equivalence was **user-confirmed**,
  not independently inspected. Cluster identity, namespace, and exact Pod count
  were not retained. No benchmark script read kubeconfigs, credentials, or API
  responses. The applications themselves used their existing connected sessions.
- Freelens was not running during two attempted starts; those attempts produced
  no measurement dataset. It was reopened before sampling. This observation does
  not establish why it exited or demonstrate a stability disadvantage.

## Results

Three consecutive approximately 60-second windows, sampled at 1 Hz. The table
pools 180 interval-end memory samples; CPU is elapsed-time weighted over the
180.15 measured seconds. These are windows in **one session**, not independent
launch trials or a statistical population.

| Metric | Iceon 0.0.6 | Freelens 1.10.3 |
| --- | ---: | ---: |
| Median physical footprint, app + attributed processes | 148.5 MiB | 398.1 MiB |
| 95th-percentile physical footprint | 149.3 MiB | 398.3 MiB |
| Observed physical-footprint range | 148.2–149.6 MiB | 322.1–402.3 MiB |
| Mean CPU, 100% = one logical core | 0.53% | 0.47% |
| 95th-percentile one-second CPU | 1.15% | 0.30% |
| CPU time over the measured windows | 0.963 s | 0.853 s |
| Accounted processes throughout capture | 5 | 5 |
| Installed regular-file bundle size | 13.7 MiB | 574.9 MiB |

Iceon's median physical footprint was **62.7% lower in this session**. Freelens's
footprint fell during capture; the observed ranges are included rather than
presenting only one snapshot. Both CPU averages were below 1% of one core. Iceon
used slightly more CPU on average here; the small absolute difference and
uncontrolled background work do not support a general CPU-efficiency ranking.

Installed bundle size measures storage, not runtime speed. Iceon relies on the
OS-provided WebKit runtime, whose installation is not charged to its app bundle;
Freelens bundles Electron. These totals are not complete dependency footprints.

**Overall performance is not established.** This capture measures settled-view
resource use, not launch time, time-to-first-Pod, refresh/API latency, search or
scroll responsiveness, frame rate, sustained load, battery use, or feature parity.
Lower memory alone does not demonstrate that one app is faster.

## Accounting and validation

The [sampler](../../tools/benchmarks/macos_apps.py) reads native
`proc_pid_rusage` v2 counters through Python `ctypes`. It does not attach a
debugger, inject JavaScript, invoke app commands, or create network requests.

- Memory uses summed `ri_phys_footprint`, not the main process alone and not RSS.
  RSS is also retained in raw data but is not the headline memory metric.
  [WebKit's memory documentation](https://docs.webkit.org/Infrastructure/MemoryInspection.html)
  describes physical footprint and its distinction from clean/reclaimable memory.
- Process membership uses macOS responsibility attribution plus recursive PPID
  descendants. Iceon's WebKit content, GPU, and networking processes are included;
  so are Freelens's Electron helpers. Each app also had an attributed
  `SetStoreUpdateService` process. Unrelated WebKit processes were excluded.
- CPU uses differences in user + system counters, converted from Mach ticks with
  `mach_timebase_info` (`125/3` ns per tick on this host). Assuming nanoseconds
  directly would undercount Apple Silicon CPU time. See the
  [osquery correction](https://github.com/osquery/osquery/pull/7473).
- A 150 ms self-calibration compared the native clock against Python's process
  CPU clock: ratio **1.00033**, within the sampler's 0.9–1.1 acceptance range.
- CPU is expressed per core: 100% means one logical core, not the whole ten-core
  machine. Child CPU is not added again through cumulative child counters.
- Process identities include PID and start time. New members are baselined, not
  charged their whole lifetime CPU; disappearing members lose their final delta.
  All five identities per app were stable within each reported window, so this
  policy did not alter these results. Very short-lived helpers can still be missed.
- Listing and counter reads are sequential, not an atomic OS snapshot. Median
  sample collection time was about 61 ms. One-minute host load ranged from
  1.25 to 2.52; other applications were not closed.
- Footprint sums are process charges, not a count of globally unique physical
  pages. Shared system services outside either app's responsibility are excluded.

An earlier validation capture exposed the Mach-clock conversion issue before
publication. Its retained ticks were converted for audit; README uses only the
fresh calibrated capture. See the [validation dataset](2026-10-29-macos-connected-pods-validation.json).
The primary [raw dataset](2026-10-29-macos-connected-pods.json) contains app
versions, executable hashes, process counters, timing, calibration, per-window
summaries, aggregate values, and limitations. It contains no process arguments,
cluster names, resource payloads, or credential data.

## Reproduce

Use a macOS machine with Python 3 and both installed apps. Connect them to the
same read-only cluster view, match namespace and Pod count, close optional docks
and inspectors, keep both windows visible, and let them settle. Do not compare a
failed/disconnected view against a working connected view.

```sh
PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover \
  -s tools/benchmarks -p 'test_macos_apps.py'

python3 tools/benchmarks/macos_apps.py \
  --rounds 3 --seconds 60 \
  --output /tmp/iceon-freelens-new-capture.json \
  --state 'User-confirmed matching connected Pods views; no interaction'
```

The sampler requires exactly one running main process at each installed path,
fails on inaccessible counters or a root restart, and refuses to overwrite an
existing result. It does not launch or build either app. Native responsibility
attribution is a macOS-specific API, not a cross-platform benchmark contract.

A stronger overall comparison still needs controlled app uptime, equal window
geometry/visibility, a recorded resource-count fixture, repeated independent
sessions in alternating order, and timed read-only interactions. This session
does not supply those controls.
